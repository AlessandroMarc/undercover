# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, so each query is written once for both databases. With `DATABASE_URL` in its environment it uses the Supabase Postgres database through the session pooler, with every table in the `undercover` schema and at most 4 connections, waiting up to two minutes for one; otherwise SQLite, as in the tests. `main.py` holds the app and the claim, document, handler and instructions operations; `runs.py` is an `APIRouter` with the operations on dispatches and evaluations; they share the `Database` dependency in `dependencies.py` and the claim views in `views.py`. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The payout rules are in `backend/payout.py`, and the scoreboard's measures in `backend/scoring.py`. The backend calls the agent's service after a sign-off and to start a dispatch or an evaluation, at `UNDERCOVER_AGENT` in the environment or `http://127.0.0.1:8002`.
- `agent/`: five parts. `api.py` is the only way the agent reaches the backend: claims, runs, its instructions, the documents, the payout rules and the records of cost and time. `tools.py` holds the claim agent's tools, the context they read and the claim graph's state, and the tools that act on the claim read it from the agent's context through `ToolRuntime`. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch or an evaluation. `service.py` is the agent's service, a FastAPI app the backend calls to start a dispatch or an evaluation and after a sign-off; in the cloud the agent runs as a service like this. `console.py` sets up the report lines and says in one line what went wrong.
  - The claim agent is a hand-written LangGraph `StateGraph`, built by `claim_graph(llm, saver)`: a node that calls the model, a `ToolNode`, a pause for a sign-off with `interrupt()`, and a node that pays. Its nodes record each reply, tool call, tool result and section read on the claim, and each model call's tokens and cost, return refusals to the model and limit the model calls. It saves its state after every step with LangGraph's `PostgresSaver` in the same Supabase database, with `durability="sync"`, so the agent always needs `DATABASE_URL`, even when the backend runs on SQLite. Each claim run gets a saver of its own on the process's shared `ConnectionPool` of at most 4 connections, since a saver lets one claim at a time read or write. The agent is synchronous throughout, because async Postgres connections don't work with Windows' default event loop.
  - The dispatcher is a LangGraph `StateGraph` with no model, in the style of `labs/week2day4.ipynb`: `list_claims` lists the claims, `fan_out` sends each to the `work_claim` node with a `Send`, `max_concurrency` caps the claim agents at once at N, and `finish_run` runs once after them all. The `work_claim` node has a `RetryPolicy` for rate limits and timeouts. It saves no progress of its own.
  - The harness's entry points are `work_claim(claim_id, run_id, graph)`, which works one claim as a new attempt, `carry_on(claim_id, run_id, graph)`, which carries a claim on from its saved progress, and `work_in_run(claim_id, run_id, new_graph)`, the one function the dispatcher calls, which does either on a graph of its own. Each times its spells of work and records them with their run.
  - Every claim graph run is traced in Langfuse, in a session named after the claim and its thread, and tagged with its run's id in `langfuse_tags`.
  - It uses `openai/gpt-6-luna` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort. Each model call's cost comes from OpenRouter's `usage.cost` on the reply. The backend's address is `UNDERCOVER_API` or `http://127.0.0.1:8000`. Like the dashboard, `uv run -m agent` reads it from the shell's environment, never `.env`; the agent's service gets `.env` from `npm run dev`.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests, with a stand-in for the agent's service.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Supabase session pooler connection string (`DATABASE_URL`) and the Langfuse keys (`LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`).
