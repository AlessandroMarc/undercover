# Tech stack

- `backend/`: FastAPI with SQLAlchemy Core, so each query is written once for both databases. With `DATABASE_URL` in its environment it uses the Supabase Postgres database through the session pooler, with every table in the `undercover` schema and at most 4 connections; otherwise SQLite, as in the tests. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The payout rules are in `backend/payout.py`. After a handler's sign-off the backend calls the agent's service, at `UNDERCOVER_AGENT` in the environment or `http://127.0.0.1:8002`.
- `agent/`: four parts. `api.py` is the only way the agent reaches the backend: claims, runs, its instructions, the documents and the payout rules. `tools.py` holds every tool, the contexts they read and the claim graph's state, and each tool reads what it needs, such as the claim a claim agent is working on, from the agent's context through `ToolRuntime`. `harness.py` builds and runs the agents. `service.py` is the agent's service, a FastAPI app that the backend calls after a sign-off; in the cloud the agent runs as a service like this.
  - The claim agent is a hand-written LangGraph `StateGraph`, built by `claim_graph(llm, saver)`: a node that calls the model, a `ToolNode`, a pause for a sign-off with `interrupt()`, and a node that pays. Its nodes record each reply, tool call, tool result and section read on the claim, return refusals to the model and limit the model calls. It saves its state after every step with LangGraph's `PostgresSaver` in the same Supabase database, with `durability="sync"`. The agent is synchronous throughout, because async Postgres connections don't work with Windows' default event loop.
  - The queue agent is LangChain's `create_agent`, with middleware that returns refusals and limits the model calls. The to-do list and the subagent are our own tools, with no other agent framework.
  - The entry points are `run_queue(cap, llm, graph)`, which runs a queue agent that hands each claim to the claim graph, `work_claim(claim_id, graph)`, which works one claim as a new attempt, and `carry_on(claim_id, graph)`, which carries a claim on from its saved progress.
  - Every claim graph run is traced in Langfuse, in a session named after the claim and its thread.
  - It uses `deepseek/deepseek-v4.1-flash` with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`. The backend's address is `UNDERCOVER_API` in the environment, not `.env`, as for the dashboard, or `http://127.0.0.1:8000`.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests, with a stand-in for the agent's service.
- `data/`: the business data the backend starts from. The agent never sees `data/evals/`, which holds the answer key.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. `.env` holds the OpenRouter key (`OPENROUTER_API_KEY`), the Supabase session pooler connection string (`DATABASE_URL`) and the Langfuse keys (`LANGFUSE_SECRET_KEY`, `LANGFUSE_PUBLIC_KEY` and `LANGFUSE_BASE_URL`).
