# Status

The claims pilot in `docs/PLAN.md` and the harness in `docs/PLAN_HARNESS.md` are built: all six phases of each are done.

The plan for durable state in `docs/PLAN_DURABLE.md` is under way: phases 1 to 4 of 6 are done: the payout rules and tracing, our records on Supabase, the claim agent as a graph that saves its progress, and a sign-off picking the claim back up.

## Running it

- `npm run dev` starts the backend on port 8000, the agent's service on port 8002 and the dashboard on http://localhost:5173. It passes `.env` to the backend and the agent's service, so it needs a `.env`, and with `DATABASE_URL` there the backend uses Supabase.
- `npm run seed` rebuilds the database `npm run dev` uses from `data/`, putting every claim back in the queue. `uv run -m backend.seed` alone never reads `.env` and rebuilds the SQLite file `undercover.db`, as the end-to-end tests do. The backend only seeds a database with no tables, so reseed after pulling a change to the tables: an older `undercover.db` lacks columns such as `runs.number`.
- `uv run -m agent` works the whole queue with the queue agent. `uv run -m agent --cap 5` works at most five claims and leaves the rest waiting. `uv run -m agent CLM-1001` works one claim with the claim agent alone. Each prints a report line per claim, and a queue run ends with its summary. All use the real model through OpenRouter.

## Built

- `backend/`: the database is seeded from `data/` (never `data/evals/`) and created on startup when it has no tables. A test checks that every operation follows the API rules.
  - Database: SQLAlchemy Core, with the tables and every query written once in `backend/database.py` for both databases. With `DATABASE_URL` set, it is the Supabase Postgres database, through psycopg and the session pooler, with every table in the `undercover` schema (`search_path` is set on each connection, keeping any settings already in the URL) and a pool of at most 4 connections. Otherwise it is SQLite at `undercover.db` or the path in `UNDERCOVER_DB`, with a connection per request. Each request runs in one transaction, committed before the response is sent. The tests and the end-to-end tests always use SQLite and never touch the network.
  - Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `list_handlers`, `list_steps`, `get_instructions`, `search_documents`, `read_section`, `get_latest_run`.
  - Payouts: `calculate_payout` works out the payout on a claim with UnderCover's payout rules in `backend/payout.py`, brought in from `labs/week2day1_payout.py`, and records nothing. Seeding stores `plans.json` in `settings`, and the approval limit comes from there too, so the rules read nothing from `data/`. Every input of the operation is required, including each field of a line.
  - Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`, `fail_claim`, `start_run`, `write_todos`, `finish_run`.
  - Claims: a claim moves from waiting to in progress. A decline or a referral is then decided. An approval stays in progress until `pay_claim` pays it, which decides it, or moves to waiting for sign-off when it pays over the limit in `company.json`. `pay_claim` refuses such a payout with a 403 until a handler signs off. A sign-off records the handler and the time on the decision, moves the claim back to in progress and pays nothing. Once it is committed, a background task asks the agent's service to pick the claim up, through `backend/agent_service.py` at `UNDERCOVER_AGENT` or `http://127.0.0.1:8002`; if the service can't be reached, the backend logs a warning and the sign-off stands. The payment shows who signed off and when. A repeat of the decision or payment already recorded returns the claim, and a different one is refused with a 409, so a step that runs again after a restart does no harm. `pay_claim` returns the claim. Each start counts as an attempt. `fail_claim` records the reason as an `error` step and puts the claim back to waiting, or after its second attempt leaves it `left_for_handler`; it refuses a claim that has a decision.
  - Runs: a run has a cap, a to-do list that `write_todos` replaces whole, and a summary recorded by `finish_run`.
  - Documents: seeding stores the policy wording and the claims manual in a `documents` table with their titles, and the backend splits both into their numbered sections. `read_section` returns one section with its document's title, and `search_documents` finds the sections that mention a word or phrase.
  - Instructions: `backend/instructions/queue.md` for running the queue and `claim.md` for working a claim. Each gives the agent its goal, what it has to work from and what done looks like, and leaves the steps to the agent and to the manual. `get_instructions` serves both, with the claim instructions followed by the contents of the wording and the manual.
- `agent/`: `api.py` is the agent's only way to the backend, with one function per operation, at `UNDERCOVER_API` in the environment or `http://127.0.0.1:8000`. `tools.py` holds every tool. `harness.py` builds and runs the agents. `uv run -m agent` loads `.env` and prints each claim's report line and the run's summary. The default model is `deepseek/deepseek-v4.1-flash` with low reasoning effort, a 120 second timeout and 5 retries, or the model in `MODEL_NAME`.
  - The claim agent is a hand-written LangGraph graph, built by `claim_graph(llm, saver)`, with a node that calls the model (`agent`), a `ToolNode` (`tools`), `wait_for_sign_off` and `pay`. Its state holds the messages, the model calls so far, and the decision and status the backend returned from `record_decision`. After a decision a decline or a referral ends the graph, an approval the backend can pay goes to `pay`, and one the backend holds for sign-off pauses at `wait_for_sign_off` with `interrupt()`; the graph never compares a payout with the limit itself. The agent node records every message and tool call as a step on the claim, and the tool node records every tool result plus a `reading` step for each section read. The backend's refusals and calls with bad arguments go back to the model, any other error stops the graph, and the agent node stops after 30 model calls, counted across restarts. Tools run one at a time, so two decisions in one reply can't race.
  - The claim agent has seven tools named after backend operations: `get_claim`, `get_policy`, `get_claim_history`, `search_documents`, `read_section`, `calculate_payout` and `record_decision`. They act on the claim in the agent's `ClaimContext`, so a claim agent can't touch another claim. It has no tool to pay: the graph pays.
  - Progress: `checkpointer()` saves the graph's state after every step (`durability="sync"`) with LangGraph's `PostgresSaver` on a pool of at most 4 connections to `DATABASE_URL`, with its tables in the `undercover` schema beside the backend's. The agent is synchronous throughout, since async Postgres connections don't work with Windows' default event loop. The tests use an `InMemorySaver`.
  - Tracing: each claim agent run is traced in Langfuse with the keys in `.env`, in a session named after the claim and its thread, such as `CLM-1001:ca130bd0-...`, as a trace named "Work claim". The run is invoked in a fresh `contextvars.Context`, so it is a root run even inside the queue agent's `work_claim` tool, which Langfuse needs to set the session. Without the keys, Langfuse prints a warning and sends nothing. The tests put a recorder in its place.
  - `work_claim(claim_id, graph)` starts the claim as a new attempt, with a new thread id, and runs the claim graph on that thread from a clean start. Any failure before the decision, or finishing without one, is recorded with `fail_claim`. A claim decided before a failure keeps its decision, the error is logged, and an approval whose payment failed stays in progress. It returns one line built from the backend's record, like `CLM-1001  approve  $420.00`, `CLM-1003  approve  $3,750.00, waiting for sign-off`, `CLM-1001  approve  $420.00, not paid yet` or `CLM-1004  failed: ..., back in the queue`.
  - `carry_on(claim_id, graph)` carries a claim in progress on from its saved progress, as the same attempt, and resumes a claim paused for sign-off past the pause, so the graph pays it. It reports like `work_claim`, as a trace named "Carry on" in the claim's Langfuse session.
  - The agent's service, `agent/service.py`, is a FastAPI app on port 8002 with `health` and `resume_claim`. `resume_claim` refuses with a 409 a claim that isn't in progress with a sign-off, and otherwise returns 202 and carries the claim on in a background task, printing the report line. It keeps the checkpointer open while it runs and builds the claim graph for each request. It never looks for other claims to carry on. `agent/console.py` sets up the report lines for both entry points.
  - `run_queue(cap, llm, graph)` first puts back any undecided claim a stopped run left in progress. It can't tell such a claim from one that `uv run -m agent CLM-...` is working at the same moment, so don't start a run while a single claim is being worked. It then starts a run and a queue agent with `list_claims`, `write_todos` and `work_claim`, which read the run from the agent's `RunContext`. The queue agent chooses the claims and their order and keeps the to-do list. `work_claim` hands each claim to the claim agent and refuses a new claim beyond the cap, and a claim the backend won't start doesn't count toward it. Claims are worked one at a time, even when the queue agent hands several over in one message, so the cap always holds. When the queue agent tries to finish with claims missed within the cap, the harness names them, oldest submitted first, at most twice. Its last reply is recorded as the run's summary, and a failure of the queue agent finishes the run with the error.
- `dashboard/`: styled to `BRAND.md` in light and dark mode. The queue and a claim page refresh every two seconds.
  - The queue (`/`): counts by state, the latest run with its to-do list and summary, and a line per claim. Claim ids in the to-do list link to the claim.
  - A claim (`/claims/:claimId`): its policy, earlier claims, the decision and payment, the sections the agent read, the agent's steps as it works, including failed attempts, and a sign-off form for a held payout. After a sign-off it says "Signed off by Dana Whitfield at 2:05 PM. Waiting for the agent to pay it.", and the payment reads "Paid $1,350.00, signed off by Dana Whitfield at 2:05 PM". It says when a claim is back in the queue after a failed attempt or left for a handler.
  - The agent's instructions (`/instructions`): for running the queue and for working a claim, read only.
- `e2e/`: tests of the three pages, the agent's steps appearing on a claim page, a handler's sign-off reaching a stand-in for the agent's service (`e2e/agent_stand_in.ts`, on port 8003), the to-do list being ticked off on the queue, and a claim that fails twice being left for a handler. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Review of the harness

On September 30, 2026, the head of engineering's review (`docs/HUMAN_REVIEW_HARNESS.md`) found that the harness was unfit for a PR:
- The agent had more than 20 hard-coded backend URLs and two ways of calling the backend.
- `queue.py` reached into `main.py`.
- The tools were spread across files, and state was passed through closures instead of LangChain's `context_schema`.
- The instructions were step-by-step scripts.

The agent was rebuilt as `api.py`, `tools.py` and `harness.py`, and the instructions were rewritten as goals. Fresh reviewers then went through the backend, the dashboard and the tests, and their fixes are in the same change.

These problems passed every check. Each phase was built, checked against its criteria and committed, and nobody read the code the way a reviewer reads a PR. `docs/CODE_STANDARDS.md` now sets the structural rules the review found broken. `docs/PROCESS.md` now requires a review by a fresh subagent before every commit, and a design in every plan.

## Last live run

On September 30, 2026, after reseeding, `uv run -m agent --cap 5` with `deepseek/deepseek-v4.1-flash` and the instructions rewritten as goals worked the five longest-waiting claims in 2 minutes 9 seconds. The decisions were the same as on September 29:
- CLM-1001 was approved and paid $420.00.
- CLM-1008 was approved for $2,240.00 and CLM-1011 for $1,150.00, both waiting for sign-off.
- CLM-1018 was referred and CLM-1010 declined.

No claim failed, and the other 20 stayed waiting. Each claim agent read 11 to 16 sections, 7 to 11 of them from the manual, where the step-by-step instructions had given 9 to 11 and 5 or 6.

An earlier run that day took 43 seconds, because the queue agent handed all five claims over at once and they ran in parallel. That exposed a race in the cap check, which the one-at-a-time rule now closes. These decisions have not yet been scored against the handlers' decisions in `data/evals/`.

For the pilot, on September 27, 2026, `uv run -m agent` with `openai/gpt-6-luna` worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer.
