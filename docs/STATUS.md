# Status

The claims pilot in `docs/PLAN.md`, the harness in `docs/PLAN_HARNESS.md` and durable state in `docs/PLAN_DURABLE.md` are built: all six phases of each are done. The swarm and the scoreboard in `docs/PLAN_SWARM.md` are built too: all six phases are done. The improver and sign-in in `docs/PLAN_IMPROVE.md` are built: all seven phases are done: handlers sign in, the claim agent's configuration is kept in versions, the platform's settings are on a Settings page, a judge grades each evaluated claim's explanation, and a senior handler runs rounds of the improver on the Improvement page, approving or rejecting each change and recipe it proposes. A dispatcher with no model works the queue with up to 25 claim agents at once, on GPT-6 Luna by default, recording the cost and time of every claim, and a Scoreboard scores evaluations on copies of the labeled claims.

## Running it

- `npm run dev` starts the backend on port 8000, the agent's service on port 8002 and the dashboard on http://localhost:5173. It passes `.env` to the backend and the agent's service, so it needs a `.env`. With `DATABASE_URL` there the backend uses Supabase; the agent's service and `uv run -m agent` always need it, since they save the claim graph's progress there.
- `npm run seed` rebuilds the database `npm run dev` uses from `data/`, putting every claim back in the queue and emptying the dispatches and evaluations. It also stores the held-out claims and the handlers' decisions on both labeled sets from `data/evals/`, which nothing else reads. It drops the old `todos` table first when it's there. `uv run -m backend.seed` alone never reads `.env` and rebuilds the SQLite file `undercover.db`, as the end-to-end tests do. The backend only seeds a database with no tables, so reseed after pulling a change to the tables.
- If you're on a free model, set `MODEL_NAME` in `.env` before `npm run seed`: seeding chooses version 1 of the claim agent and the models allowed from it.
- Every page needs a signed-in handler. Sign in on `/sign-in` with a handler's email from `data/handlers.json` and the password set for them in Supabase Auth (`HANDLER_PASSWORD` in `.env`). There's no sign-up. Dana Whitfield is the only handler who can sign off payouts over the limit.
- On the queue page, choose the claim agents at once, from 1 to 25, and press Start a dispatch. The backend asks the agent's service, which works every claim in progress and every waiting claim with up to N claim agents at once. Only one dispatch, evaluation or stretch of a round runs at a time, and a start while the service isn't running says so. On the Scoreboard, choose a labeled set, all its claims or the five tiny ones, and the claim agents at once, and press Start an evaluation. `uv run -m agent CLM-1001` works one claim with no run, printing its report line. All three use the real model through OpenRouter and save the claim graph's progress in Supabase.
- On the Improvement page, a handler who can sign off over the limit presses Start a round. The round runs the first evaluations the current version needs, then the improver proposes a change, which shows with its diff and reason for the handler to approve, after confirming, or reject with a reason. An approved change is evaluated and kept or rolled back by the business's rule, then the improver proposes a new recipe for the next round. Stop the round ends it at any point. Every round costs at most the spending limit in the settings, $0.50 to start with.
- A payout over the limit waits for a handler to sign it off on its claim page. With `npm run dev` running, the agent's service then pays it within a second or two; otherwise the next dispatch does.

## Built

- `backend/`: the database is seeded from `data/` and created on startup when it has no tables. Only seeding reads `data/evals/`. A test checks that every operation follows the API rules. `main.py` holds the app and the claim, document and handler operations; `runs.py` is an `APIRouter` with every operation under `/api/runs`, `/api/dispatches` and `/api/evaluations`; `configuration.py` is an `APIRouter` with the claim agent's versions; `improvement.py` is an `APIRouter` with the rounds of the improver, the agent's service's operations under `/api/rounds` and the dashboard's under `/api/improvement`. They share the `Database` and `SignedIn` dependencies in `dependencies.py`, `to_claim()` and `to_summary()` in `views.py`, finding a run or a version and the not-found messages in `lookups.py`, reading runs in `scoreboard.py` and `now()` in `database.py`, and no router uses another's helpers. Claim and run statuses, decisions, run kinds and labeled sets are `StrEnum`s in `models.py`.
  - Database: SQLAlchemy Core, with the tables and every query written once in `backend/database.py` for both databases. With `DATABASE_URL` set, it is the Supabase Postgres database, through psycopg and the session pooler, with every table in the `undercover` schema (`search_path` is set on each connection, in place of any `options` in the URL and keeping its other settings, such as `sslmode`) and a pool of at most 4 connections, waiting up to two minutes for one. Otherwise it is SQLite at `undercover.db` or the path in `UNDERCOVER_DB`, with a connection per request. Each request runs in one transaction, committed before the response is sent. The tests and the end-to-end tests always use SQLite and never touch the network.
  - Sign-in: `backend/auth.py` checks a Supabase access token with PyJWT's `PyJWKClient` against the project's public keys at `VITE_SUPABASE_URL`, with the audience `authenticated` and 30 seconds of clock leeway, and returns its email; nothing else reads the address. `SignedIn` in `dependencies.py` finds the handler by that email (401 without a valid token, 403 for an email that isn't a handler's). `get_signed_in_handler` (`GET /api/me`) returns the handler with their email and whether they can sign off over the limit. `sign_off_claim`, `start_dispatch` and `start_evaluation` need a signed-in handler; reads and the agent's service's writes stay open until Week 3. Seeding stores each handler's email, and only Dana Whitfield can sign off over the limit.
  - Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `get_settings`, `list_steps`, `get_current_version`, `get_version`, `get_configuration`, `get_version_details`, `search_documents`, `read_section`, `get_latest_dispatch`, `list_evaluations`, `get_evaluation`.
  - Settings: `settings` keeps the platform's settings as a history, one row per change with who made it and when; the newest row is in force. Seeding makes row 1 with the approval limit from `data/company.json` and the rest from `data/improvement.json`: the objectives on the held-out set, the noise and the tolerance, the spending limit for each round and the claim agents at once in the improver's evaluations. `data/models.json` gives the models the claim agent may use, with their reasoning efforts and prices, seeded into `models_allowed` (with `MODEL_NAME` set, that model alone at `default` and a price of 0). `get_settings` returns the settings in force, every change and the models allowed; `change_settings` (`PUT /api/settings`) records a new row, and only a handler who can sign off payouts over the limit may use it (`senior(action)` in `dependencies.py`, which names the action in its 403).
  - The judge: `backend/judge.py` is the one module that calls Jev (`typesafe/jev-1.13`) through OpenRouter's Decisions endpoint with the `openrouter` package, at `JUDGE_URL` or `https://openrouter.ai`, with the lab's rubric and three questions, a 10 second timeout and no retries. It grades the agent's reason and section against the handler's reason and reference, which seeding stores in `handler_decisions`; the score is Jev's score from 0 to 3, the letter the likeliest level, and the two checks, same grounds and same section, are kept as probabilities. `finish_run` grades an evaluation's copies in parallel, one thread each, before it finishes: an undecided copy gets an F without asking the judge, and a copy the judge can't grade is recorded with no grade and logged. `grades` holds each copy's grade and the judge's cost. An evaluation's grade averages its graded copies, and its judge cost is apart from its model cost. With `MODEL_NAME` set there's no judge, and nothing is graded.
  - Payouts: `calculate_payout` works out the payout on a claim with UnderCover's payout rules in `backend/payout.py`, brought in from `labs/week2day1_payout.py`, and records nothing. Seeding stores `plans.json` in `payout_rules`, and the approval limit comes from the settings in force, so the rules read nothing from `data/`. A new approval limit applies to the decisions recorded after it. Every input of the operation is required, including each field of a line.
  - Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`, `fail_claim`, `record_model_call`, `record_work_time`.
  - Cost and time: `record_model_call` records one model call's input and output tokens and its cost in US dollars on a started claim, in `model_calls`, and `record_work_time` one spell of the agent's work, in `work_times`, with its start worked out from the time it's recorded less its seconds. Each has the claim's thread and the run it happened in, or none.
  - Claims: a claim moves from waiting to in progress. A decline or a referral is then decided. An approval stays in progress until `pay_claim` pays it, which decides it, or moves to waiting for sign-off when it pays over the limit in `company.json`. `pay_claim` refuses such a payout with a 403 until a handler signs off. A sign-off records the signed-in handler and the time on the decision, moves the claim back to in progress and pays nothing. Once it is committed, a background task asks the agent's service to pick the claim up, through `backend/agent_service.py` at `UNDERCOVER_AGENT` or `http://127.0.0.1:8002`; if the service can't be reached, the backend logs a warning and the sign-off stands. The payment shows who signed off and when. A repeat of the decision or payment already recorded returns the claim, and a different one is refused with a 409, so a step that runs again after a restart does no harm. `pay_claim` returns the claim. Each start counts as an attempt. `fail_claim` records the reason as an `error` step and puts the claim back to waiting, or after its second attempt leaves it `left_for_handler`; it refuses a claim that has a decision.
  - Starting: `start_dispatch` (`POST /api/dispatches`, body `{agents}`) asks the agent's service to start a dispatch through `backend/agent_service.py`, writes nothing and returns 202. It passes on the service's 409, and returns 503 with "The agent's service isn't running" when the service can't be reached.
  - Runs: a run is a dispatch or an evaluation, with a number, its N claim agents at once, the version of the claim agent it used with that version's model and reasoning effort, which the backend records when the run is created, a status (running, finished or stopped), its start and finish, and its claims in order in `run_claims`. Only the agent's service writes them: `create_dispatch`, `create_evaluation`, `record_run_claims`, `finish_run` and `stop_runs`, under `/api/runs`. A run in a response has each claim's line from the queue with its start, seconds and model cost in the run, the run's model cost, and its seconds once it finishes. `finish_run` builds a dispatch's summary from its claims as they stand, counting each claim once: approved, declined and referred, the payouts waiting for a sign-off (counted as approved), the claims left for a handler, and the unfinished ones, in progress or back in the queue, for the next dispatch. `stop_runs` marks every running run stopped.
  - Evaluations: `create_evaluation` records an evaluation of the evaluation set (the queue's 25 claims) or the held-out set (in `held_out_claims`), whole or its five `tiny` claims, and makes a waiting copy of each claim, oldest submitted first, with an id like `CLM-1104-E7` written into its record too. Copies are rows in `claims` with `evaluation_id` and `copy_of`, so every claim operation works on them, but `list_claims` leaves them out and `sign_off_claim` refuses one with a 409. `start_evaluation` asks the agent's service, like `start_dispatch`. `list_evaluations` and `get_evaluation` score each evaluation from its copies as they stand and the handlers' decisions in `handler_decisions`, with the lab's measures in `backend/scoring.py`: decision accuracy, accuracy (a payout within a dollar), the cost of mistakes ($1,500 a wrongful decline, a wrongful approval's payout, $50 a needless referral, the difference on a right approval), the straight-through rate, model cost and time per claim, and the run's time. A copy the agent didn't decide counts as a referral. No response the agent's service reads holds anything from `handler_decisions`.
  - Documents: seeding stores the policy wording and the claims manual in a `documents` table with their titles, and the backend splits both into their numbered sections. `read_section` returns one section with its document's title, and `search_documents` finds the sections that mention a word or phrase.
  - The configuration in versions: the claim agent's instructions, model and reasoning effort are kept in `versions`, each with what it changed from the version it was based on, its reason, who proposed and approved it and when, and its verdict. Version 1 is seeded from `backend/instructions/claim.md`, which gives the claim agent its goal, what it has to work from and what done looks like, on `openai/gpt-6-luna` at low reasoning effort. With `MODEL_NAME` set when seeding, version 1 is that model at `default`, with no reasoning effort sent; `backend/free_models.py` is the only code that reads `MODEL_NAME`, so set it in `.env` before `npm run seed`. The current version is the newest kept one. `get_current_version` and `get_version`, which the claim agent's client reads, hold the number, the instructions followed by the contents of the wording and the manual, the model and the reasoning effort, and no scores. `get_configuration` and `get_version_details` add each version's status, its diff from the version it was based on (`backend/diffs.py`, from `difflib.unified_diff` with two lines of context), and its scores: the averages of the finished whole-set evaluations rounds ran on it, empty until rounds exist.
  - Rounds of the improver: `rounds` records each round with who started it, the settings, recipe and version in force, the improver's model (`openai/gpt-6-luna` at medium, or the model in `MODEL_NAME` at `default`), its thread and the first evaluations the current version still needs, one on the evaluation set and two on the held-out set. One round is open at a time. `proposals` holds the improver's proposals, a change (instructions, model, reasoning effort, reason) or a recipe, and each one's review; `recipes` holds the recipe's versions, seeded from `backend/instructions/recipe.md`, and `improver_calls` the improver's model calls. `round_state.py` works out where a round has got to from these records (`first_evaluations`, `improving`, `change_waiting`, `evaluating`, `verdict`, `recipe_waiting`), and stopping a round rolls back a version it hasn't given a verdict. A proposal changes nothing, a change to a model outside the models allowed is refused as it's proposed, and a round has one approved change at most: once a handler who can sign off over the limit approves it, `create_version` makes it a version under test, refusing a model outside the models allowed with a 422. `record_review` and the dashboard's `approve_proposal` and `reject_proposal` name the proposal, and refuse with a 409 one that isn't waiting. `create_round_evaluation` makes a round's next evaluation at its agents at once, choosing its set itself: its starting version on the sets of its first evaluations, then its version under test once on the evaluation set and twice on the held-out set until the verdict, so a version's scores never change after it, refusing a version's first one when the three could cost more than what's left of the limit, estimated from the highest cost per claim seen on the version's model or, with none, on another model scaled by its prices (`spending.py`). A round's cost is its improver calls, its evaluations' model calls and the judge; once it reaches the limit, `start_claim` refuses a new claim in its evaluations and the evaluation finishes stopped, which stops a round still in its first evaluations. `record_verdict` keeps or rolls back the version by the rule in `verdict.py`, on the averages of its held-out evaluations against the current version's. `get_improver_view` gives the improver the current version, its scores, the evaluation set's wrong claims and the five right ones explained least well beside the handlers' reasons, the earlier rounds, the settings, the rule, the spending and the models allowed, and nothing from the held-out set but scores. `get_improvement` gives the dashboard the open or newest round with its stage, progress, proposal waiting and diff, evaluations and cost, every round, the versions tried and the recipes. `start_round` and `stop_round` need a handler who can sign off over the limit, and `start_round`, `approve_proposal` and `reject_proposal` reach the agent's service through `agent_service.py`.
- `agent/`, in six parts: `connection.py` holds the one client to the backend, at `UNDERCOVER_API` or `http://127.0.0.1:8000`, and `api.py` has the claim agent's and the service's operations on it, one function each; `improver_api.py` has the improver's, and `api.py` has no way to the rounds, the scores or the settings. Its client retries a refused connection five times, about 7 seconds, since the service calls the backend as it starts. `uv run -m agent` reads `UNDERCOVER_API` from the shell's environment, never from `.env`, because `api.py` reads it before the command line loads `.env`; the agent's service gets it from `.env` through `npm run dev`. `tools.py` holds the claim agent's tools and the context and state they read. `harness.py` builds and runs the claim agent. `dispatcher.py` works a dispatch or an evaluation. `improver.py` is the improver. `service.py` is the agent's service. `console.py` sets up the report lines and says in one line what went wrong. The agent's service creates each run, reads its version with `get_version` and builds the run's claim agents from it: its model through `agent/openrouter.py`, at its reasoning effort (`default` sends none), with a 120 second timeout and 5 retries, and its instructions. A resume after a sign-off and `uv run -m agent CLM-1001` use the current version. The agent no longer reads `MODEL_NAME`.
  - The claim agent is a hand-written LangGraph graph, built by `claim_graph(llm, saver)`, with a node that calls the model (`agent`), a `ToolNode` (`tools`), `wait_for_sign_off` and `pay`. Its state holds the messages, the model calls so far, and the decision and status the backend returned from `record_decision`. After a decision a decline or a referral ends the graph, an approval the backend can pay goes to `pay`, and one the backend holds for sign-off pauses at `wait_for_sign_off` with `interrupt()`; the graph never compares a payout with the limit itself. The agent node records every message and tool call as a step on the claim, and the tool node records every tool result plus a `reading` step for each section read. The backend's refusals and calls with bad arguments go back to the model, any other error stops the graph, and the agent node stops after 30 model calls, counted across restarts. Tools run one at a time, so two decisions in one reply can't race.
  - The agent writes the JSON it hands a model and records as a step with characters such as § and ’ as themselves (`agent/json_text.py`), so the steps read as the model wrote them.
  - The claim agent has seven tools named after backend operations: `get_claim`, `get_policy`, `get_claim_history`, `search_documents`, `read_section`, `calculate_payout` and `record_decision`. They act on the claim in the agent's `ClaimContext`, so a claim agent can't touch another claim. It has no tool to pay: the graph pays.
  - Progress: `checkpoint_pool()` opens the process's pool of at most 4 connections to `DATABASE_URL`, waiting up to two minutes for a connection, and sets up LangGraph's `PostgresSaver` once, with its tables in the `undercover` schema beside the backend's. `claim_graphs(llm, pool)` builds a claim graph with a saver of its own for each claim run, since a saver lets one claim at a time read or write. The graph saves its state after every step (`durability="sync"`). The agent is synchronous throughout, since async Postgres connections don't work with Windows' default event loop. The tests use an `InMemorySaver`.
  - Cost and time: after each model call the agent node records the reply's `prompt_tokens`, `completion_tokens` and `cost` from `response_metadata["token_usage"]`, which carries OpenRouter's `usage`. `work_claim` and `carry_on` time each spell of work with `time.monotonic()` and record it however it ends, after the claim is settled, so a wait for a sign-off is never counted. Both carry the run's id from `ClaimContext`, or none for `uv run -m agent CLM-1001` and a resume after a sign-off.
  - Tracing: each claim agent run is traced in Langfuse with the keys in `.env`, in a session named after the claim and its thread, such as `CLM-1001:ca130bd0-...`, as a trace named "Work claim". A claim worked in a run has `langfuse_tags: [run_id]` in its metadata. The run is invoked in a fresh `contextvars.Context`, so it is a root run even inside the dispatcher, which Langfuse needs to set the session. Without the keys, Langfuse prints a warning and sends nothing. The tests put a recorder in its place.
  - `work_claim(claim_id, run_id, graph)` starts the claim as a new attempt, with a new thread id, and runs the claim graph on that thread from a clean start. Any failure before the decision, or finishing without one, is recorded with `fail_claim`, except a rate limit or a timeout (`TRANSIENT`), which is raised again with the claim left in progress and its progress saved. A claim decided before a failure keeps its decision, the error is logged, and an approval whose payment failed stays in progress. It returns one line built from the backend's record, like `CLM-1001  approve  $420.00`, `CLM-1003  approve  $3,750.00, waiting for sign-off`, `CLM-1001  approve  $420.00, not paid yet` or `CLM-1004  failed: ..., back in the queue`.
  - `carry_on(claim_id, run_id, graph)` carries a claim in progress on from its saved progress, as the same attempt, on the same thread. A claim at the pause has been signed off, so it resumes past the pause and the graph pays it. A claim with nothing saved and no decision starts from the beginning on its thread. Any other carries on from its last saved step, finishing a step whose writes were saved before its checkpoint, so a claim stopped mid-node re-runs only that node; the backend treats a repeated decision or payment as done. The model call limit counts across a restart. It reports like `work_claim`, as a trace named "Carry on" in the claim's Langfuse session. `work_in_run(claim_id, run_id, new_graph)` builds a claim graph and carries the claim on if it is in progress or starts it if it is waiting: it's the one function the dispatcher calls. When the claim is an evaluation's copy held for sign-off, it deletes the claim's thread from the checkpointer, since nobody can sign a copy off.
  - The dispatcher is a LangGraph graph with no model, in the style of `labs/week2day4.ipynb`. For an evaluation, `list_claims` takes its copies, which the backend made. For a dispatch it lists the queue's claims in progress and waiting, oldest submitted first, leaving out any the service is resuming after a sign-off, and records them with the dispatch. `fan_out` sends each to `work_claim` with a `Send`, or goes straight to `finish_run` when there are none, and LangGraph runs up to N `work_claim` tasks at once (`max_concurrency`). `work_claim` calls `work_in_run`, and once more when the claim's first attempt failed and put it back in the queue. Its `RetryPolicy` tries a claim three times in all on a rate limit or a timeout, waiting about 10 seconds then 20, and each retry carries the claim on. On the last try, and for any other error, it reports the claim "left for the next dispatch", or "left in progress" for an evaluation's copy, and the run goes on. The service binds the harness's `work_in_run` to its claim graphs and hands it to the dispatcher. `finish_run` runs once, after every claim. The dispatcher saves no progress of its own. The tests run the `RetryPolicy` with its waits at zero.
  - The improver, `agent/improver.py`, is a LangChain agent (`create_agent`) on the round's model, with its instructions from the round and four tools: `read_results`, `propose_change`, `run_evaluation` and `propose_recipe`. `HumanInTheLoopMiddleware` pauses it at `propose_change` and `propose_recipe` for a handler, except for a model outside the models allowed, which the tool answers with "isn't allowed" and records nothing; its progress is saved in the checkpointer on the round's thread, and a review resumes it with `Command(resume=...)`, a rejection reaching it as the tool's answer with the handler's reason. `ModelCallLimitMiddleware` stops it after 20 model calls in a round, one tool call runs at a time, a stopped round ends it before its next model call, and each model call is recorded with `record_improver_call`. `run_evaluation` asks for the version's three evaluations one at a time, works each through the dispatcher and asks for the verdict. Each stretch of its work is traced as "Improver" in the session `Round N:<round_id>`, and its evaluations' claims carry the run and the round in `langfuse_tags`.
  - The agent's service, `agent/service.py`, is a FastAPI app on port 8002 with `health`, `resume_claim`, `start_dispatch`, `start_evaluation`, `start_round` and `review_proposal`. One thing runs at a time: a dispatch, an evaluation or a stretch of a round, and a start refuses with a 409 that names what is running, such as "A dispatch is running". `start_round` creates the round, works its first evaluations through the dispatcher, then runs the improver until it pauses for a handler or ends, recording a proposal and letting go of the lock while it waits; `review_proposal` records the review and resumes it. A proposal the backend refuses, such as a second change, goes back to the improver as a rejection with the backend's reason. `start_dispatch` returns 202 and, in a background task, creates the dispatch with the model's name and reasoning effort and works it. A dispatcher that fails marks the run stopped, and the next start is accepted. `resume_claim` refuses with a 409 a claim that isn't in progress with a sign-off, and otherwise returns 202 and carries the claim on in a background task, keeping dispatches away from it meanwhile. As it starts, the service opens the checkpoint pool, marks any run still running as stopped, and stops any open round that isn't waiting for a handler, whose improver's progress is saved.
- `dashboard/`: styled to `BRAND.md` in light and dark mode. Every page but the Settings page refreshes every two seconds. Every page has a `PageHeader` with its title and a line on what it's for. Loading, empty and error states use `StateMessage` and say what to do next, offering a reload for a server error. Numbers in tables are right-aligned in JetBrains Mono with tabular figures, and a table whose cells fill in as the page refreshes, an evaluation's claims, keeps set column widths and two lines for the agent's reason, so nothing moves. Every button has the same height, radius and font, and the page titles, panels and tables' first columns line up on every page.
  - Sign-in (`/sign-in`): `dashboard/src/auth.ts` is the only module that uses `@supabase/supabase-js`, from `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`. `RequireHandler` sends a visitor who isn't signed in to the sign-in page and back to the page they asked for, and gives every page the signed-in handler. The header shows the handler's name and role and Sign out. `api.ts` sends the session's access token with every request. Vite reads `.env` from the repo root in development mode only, so the checks never read it.
  - The queue (`/`): counts by state, the dispatch panel and a line per claim. The panel has a form, "Claim agents at once" from 1 to 25 with 3 chosen, and a Start a dispatch button that shows the backend's refusal in an alert. It shows the latest dispatch: its number and status, when it started and with how many claim agents, its model cost, each of its claims with a link, its state, decision, payout, time and model cost, and once it finishes its time and summary. Before the first it says "No dispatch yet." and how to start one.
  - A claim (`/claims/:claimId`): on the left, the claim, its items and documents, its policy, the customer's earlier claims and the sections the agent read; on the right, the decision and payment, with a sign-off form for a held payout, and the agent's steps as it works, including failed attempts. What changes as the agent works grows at the end of its column, so nothing moves above it. A handler who can sign off over the limit signs it off as themselves; anyone else sees "Only a handler who can sign off payouts over $1,000.00 can sign this off. Marcus Oyelaran can't." and no button. After a sign-off it says "Signed off by Dana Whitfield at 2:05 PM. Waiting for the agent to pay it.", and the payment reads "Paid $1,350.00, signed off by Dana Whitfield at 2:05 PM". It says when a claim is back in the queue after a failed attempt or left for a handler.
  - The Scoreboard (`/scoreboard`): a form to start an evaluation (the evaluation set or the held-out set, all 25 claims or the five tiny ones, and the claim agents at once), and the evaluations, newest first, with their set, size, start, version, round if a round ran it, N, model and reasoning effort, status and eight measures, the grade shown like 2.20 or "Not graded".
  - An evaluation (`/scoreboard/:runId`): its measures, including the grade, its model cost and judge cost, and each copy beside the handler's decision and payout, with a Right or Miss chip, the judge's grade chip (A Sea Green, B Cerulean, C Marigold, F Raspberry) and score, Same grounds and Same section as Yes or No, its mistake cost, model cost, time and the agent's reason. A claim the agent didn't decide shows "No decision".
  - A copy's claim page says "A copy of CLM-1104 in an evaluation", linking to the evaluation, and has no sign-off form: a held approval says it counts as finished.

## Known gaps

- A claim with a decision but nothing saved on its thread, which only happens when someone approves a claim through the API by hand, can't be carried on: each run logs the error and leaves it in progress.
- If two processes carry the same claim on at the same moment, which the harness can't rule out, the backend still decides and pays it once. The second process's decision or payment, arriving while the first is being saved, is refused with an error, and that process logs it.
- A handler can only sign off a held payout; rejecting one comes later.
- The dispatcher's worker re-raises a rate limit or a timeout until its last try, rather than using LangGraph's `error_handler`: in LangGraph 1.2.12 a handled error is still raised from `invoke` when the worker runs beside others. A test records this, so a release that fixes it shows up.
- `uv run -m agent CLM-1001` beside a dispatch can work the same claim at the same moment; the backend still decides and pays it once.
- At 25 claim agents at once each step outside the model takes about 2.6 times as long as at 3 (0.37 against 0.14 seconds), most likely from waiting on the 4 connections a process to Supabase (see the live run below). The model itself is no slower.
- GPT-6 Luna sometimes ends its turn with a message instead of recording a decision: 4 times in the live runs below. The harness fails that attempt and the dispatch works the claim once more. A claim this happens to twice is left for a handler, as CLM-1017-E3 was.
- Langfuse loses the traces of claims stopped by `kill -9` before the service's client sent them.
- An improver call answered just as a handler stops the round isn't recorded, since a stopped round records nothing more, so the round's cost can be short by that one call. The stretch ends there.
- The agent's service's own operations, such as `record_review` and `create_round` under `/api/rounds`, and the claim workflow's, are open until Week 3 brings it an API key, as the plan leaves them: anyone who can reach the backend could record a review in a handler's name. Every operation a handler takes on the dashboard checks the signed-in handler.
- Two senior handlers saving the settings at the same moment: the later save is built on the settings as its page loaded them, so it can undo the other's change.
- In a production build the page can paint once before `theme.ts` sets a saved appearance that differs from the computer's.
- A refused sign-off says the approval limit in force now, not the one the payout was held under, if they differ.
- The Improvement page re-scores every round's evaluations on each two-second refresh, which grows with the rounds run.
- A claim's decision arriving moves the agent's steps below it down once, by the decision's height: it's new content, and keeping room for a decision would leave a large empty panel on every claim. While an evaluation runs, a copy's own cost and time grow in place in their right-aligned cells.
- Rounds can't run on free models, which allow fewer requests in a day than a round needs; students on free models build and test everything.
- Stopping `npm run dev` with SIGTERM twice left a uvicorn reloader holding its port with no worker; `kill -9` on it cleared the port.

## Supabase

The backend's tables and the checkpointer's are in the `undercover` schema. Row Level Security is off on them, and Supabase's table listing warns about that, but the schema isn't exposed through Supabase's Data API: the `anon`, `authenticated` and `service_role` roles have no access to it, and Supabase's security advisor reports nothing. The backend and the agent connect as `postgres`, the tables' owner.

## Review of the harness

On September 30, 2026, the head of engineering's review (`docs/HUMAN_REVIEW_HARNESS.md`) found that the harness was unfit for a PR:
- The agent had more than 20 hard-coded backend URLs and two ways of calling the backend.
- `queue.py` reached into `main.py`.
- The tools were spread across files, and state was passed through closures instead of LangChain's `context_schema`.
- The instructions were step-by-step scripts.

The agent was rebuilt as `api.py`, `tools.py` and `harness.py`, and the instructions were rewritten as goals. Fresh reviewers then went through the backend, the dashboard and the tests, and their fixes are in the same change.

These problems passed every check. Each phase was built, checked against its criteria and committed, and nobody read the code the way a reviewer reads a PR. `docs/CODE_STANDARDS.md` now sets the structural rules the review found broken. `docs/PROCESS.md` now requires a review by a fresh subagent before every commit, and a design in every plan.
